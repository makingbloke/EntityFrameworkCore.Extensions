# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

EntityFrameworkCore.Extensions is a library of extension/helper methods for Entity Framework Core 11 (targeting net11.0, set once in `Directory.Build.props`), supporting **SQL Server and SQLite only**. It adds capabilities EF Core doesn't provide natively: database-independent free text search, table hints, ExecuteUpdate/Delete/Insert variants that return affected rows, unique constraint violation detection, case-insensitive collation helpers, and raw-SQL execute/paging helpers.

Solution layout (`EntityFrameworkCore.Extensions.slnx`):
- `DotDoc.EntityFrameworkCore.Extensions` — the library.
- `DotDoc.EntityFrameworkCore.Extensions.Tests` — MSTest test suite (has `InternalsVisibleTo` access to the library).

## Common commands

Build and test via the solution file (`.slnx`):

```
dotnet build EntityFrameworkCore.Extensions.slnx
dotnet test EntityFrameworkCore.Extensions.slnx
```

Run a single test class or method:

```
dotnet test --filter "FullyQualifiedName~TableHintsTests"
dotnet test --filter "FullyQualifiedName~TableHintsTests.MethodName"
```

Tests run against **both SQLite and SQL Server** (most tests have a `[DataRow]` for each of `DatabaseTypes.Sqlite` / `DatabaseTypes.SqlServer`; only `TableHintsTests` uses `DynamicDataAttribute`). Each database's connection string comes from an environment variable, `DOTDOC_EFCORE_TESTS_SQLITE` / `DOTDOC_EFCORE_TESTS_SQLSERVER` (the names are constants in `DotDoc.EntityFrameworkCore.Extensions.Tests/Data/DatabaseUtils.cs`), and `DatabaseUtils` fills in the test specific parts: the SQL Server database name, and the SQLite data source (a file in the test's temporary directory, so for SQLite `;` is enough). If a database's variable is missing or empty, its tests are turned off (reported as inconclusive by `DatabaseUtils.GetSqliteConnectionString` / `GetSqlServerConnectionString`), so either database's tests can run without the other. The variables are set in `DotDoc.EntityFrameworkCore.Extensions.Tests/test.runsettings` (`RunConfiguration` / `EnvironmentVariables`), which is checked in and used by `dotnet test` and Visual Studio through `RunSettingsFilePath` in the test project; its values replace any set on the machine. Every test that connects to a database must get its connection string from `DatabaseUtils` (`GetConnectionString`, or `GetSqliteConnectionString` / `GetSqlServerConnectionString` for a database of its own); a context that only generates SQL (`ToQueryString`) can use a dummy one. A database added later (e.g. PostgreSQL) should follow the same pattern, with its own `DOTDOC_EFCORE_TESTS_<DATABASE>` variable. Each test run drops/recreates the database via `EnsureDeletedAsync`/`EnsureCreatedAsync`. SQLite tests need no external service: each test's database is a file in its own `TestContext.TestTempDirectory`, so `DatabaseUtils.OpenDatabaseAsync` and `GetConnectionString` take the test's `TestContext` (which also gives the cancellation token). MSTest deletes the directory after a test that passes and keeps it after a failure; `Data/SqliteTestCleanup.cs` clears the SQLite connection pools after every test (`[GlobalTestCleanup]`), because a pooled connection keeps the file open and the directory couldn't be deleted.

FreeText search tests additionally require a full-text catalog (SQL Server) or FTS5 virtual tables (SQLite), both set up automatically by `DatabaseUtils.OpenDatabaseAsync`.

`TreatWarningsAsErrors` is enabled solution-wide (`Directory.Build.props`), along with StyleCop (`NewStyleCop.Analyzers`) and `SonarAnalyzer.CSharp` as global analyzers — expect a normal build to fail on style/analyzer violations, not just compile errors.

## Architecture

### Per-database-provider dispatch

Almost every feature branches on database provider via `DatabaseTypeExtensions.GetDatabaseType()` (`DatabaseType/`), which inspects the active `DbContextOptions`/`DatabaseFacade`/`MigrationBuilder` and returns `DatabaseTypes.Sqlite` or `DatabaseTypes.SqlServer`. Unsupported providers throw `UnsupportedDatabaseTypeException`. Most public `UseXxxExtensions(DbContextOptionsBuilder)` setup methods switch on this to install the correct provider-specific service (interceptor, translator provider, query generator).

### Custom query generator + SQL tagging pattern

Several features (table hints, ExecuteUpdate/Delete/Insert-with-results, SQLite free text search with stemming, below) work by replacing EF's `IQuerySqlGeneratorFactory` with a custom one (`CustomQueryGenerators/`, installed via `CustomQueryGeneratorExtensions.UseCustomQueryGenerator`). The generic flow:

1. A LINQ query is tagged with the `CustomTagExtensions.TagWithTableHints` / `TagWithExecuteUpdate` extension methods, which call `.TagWith(...)` with a magic string prefix. The prefixes are private to `CustomTagExtensions`, which is the only class that knows the tag format: it creates the tags, recognises them (`IsExecuteUpdateTag` / `IsTableHintsTag`) and reads them (`GetCustomTags`).
2. The provider-specific query generator (`SqlServerCustomQueryGenerator` / `SqliteCustomQueryGenerator`) recognizes the tag while generating SQL and rewrites the statement (e.g. injects `WITH (NOLOCK)` table hints). Its `GenerateTagsHeaderComment` override calls `CustomTagExtensions.GetCustomTags`, which returns a `CustomTags` holding the custom values and a copy of the set without the custom tags, so they never appear in the SQL (the cached set must not be changed).
3. The ExecuteXxx variants are told apart only by their tag (e.g. `$$EXECUTEUPDATE<guid>$$UpdateGetRows`; the suffix is a `QueryType` value). The `<guid>` in each prefix is a random GUID made once for each process, so only tags made by `CustomTagExtensions` are recognised; tests must never write the prefixes themselves. The variant **must** be in the expression: EF caches the generated SQL against the expression tree, so anything outside it (a past version used an `AsyncLocal`) lets the first variant to run decide the SQL for every later call with the same query shape. For the same reason the generators must never use per-call state.
4. For "get rows back" operations (`ExecuteDeleteGetRowsAsync`, `ExecuteInsertGetRowAsync`, `ExecuteUpdateGetRowsAsync`), the per-call state is `ExecuteUpdateState`, a scoped service in EF's internal service provider (one per `DbContext`), registered by `ExecuteUpdateOptionsExtension` from `UseExecuteUpdateExtensions()`. It is also registered as `IResettableService` (resolving to the same instance) so a pooled context is reset when it goes back to the pool. The method sets the query type, a `DbCommandInterceptor` (`ExecuteUpdateInterceptor`, which finds the state through `eventData.Context`) captures the generated SQL/parameters from the real EF `ExecuteUpdate`/`ExecuteDelete` pipeline *and suppresses execution* (`InterceptionResult.SuppressWithResult`), then the extension method re-runs the captured SQL itself via `SqlQueryRaw` to materialize and return the affected rows. Follow this pattern exactly when touching this code: check for re-entrancy (throw if the query type isn't `Unknown`) and set the query type **before** the `try`, and always reset the state in the `finally`.
5. If `ExecuteUpdateState` can't be found, `UseExecuteUpdateExtensions()` wasn't called. Every method that depends on the custom generator (all except `ExecuteDeleteGetCountAsync` / `ExecuteUpdateGetCountAsync`) throws an `InvalidOperationException` before running anything; without the generator, `ExecuteInsertAsync` would run as an UPDATE of every matching row.
6. This depends on **EF Core 11**. EF 10 drops the tags of an `UpdateExpression` when a visitor rebuilds it (e.g. an `==` in the `Where`), so the generator never sees the tag (EF issue #36908, fixed in 11.0.0). Don't target EF 10 again; see ChangeLog 6.0.0.2 for the history.

Note `ExecuteUpsertGetCountAsync`/`ExecuteUpsertGetRowsAsync` implement upsert as an explicit transaction (update-then-insert-if-zero-rows) rather than native `MERGE`/`ON CONFLICT`, specifically so update and insert can target different property sets — see the code comment in `ExecuteUpdateExtensions.cs` for the reasoning.

### Free text search translation

`FreeTextSearchFunction/` and `MatchFunction/` add custom `EF.Functions.*` methods translated per-provider by `IMethodCallTranslator` implementations (`SqlServerFreeTextSearchTranslator`, `SqliteFreeTextSearchTranslator`, `MatchTranslator`). Each is exposed through an `IMethodCallTranslatorPlugin` (`...TranslatorPlugin`) that the `Use...` method registers with `TranslatorExtensions.AddMethodCallTranslatorPlugin<TPlugin>()` (`Utilities/`), via the generic `MethodCallTranslatorPluginOptionsExtension<TPlugin>`. **Never register translators by replacing `IMethodCallTranslatorProvider`** (`ReplaceService`): a replacement deriving from `RelationalMethodCallTranslatorProvider` drops all of EF's database-specific translations (string methods, `Math`, `DateTime`...), and only one replacement can be active, so two features replacing it break each other (this was a bug fixed in 7.0.0.0). Plugins are asked before EF's own translators, add to them rather than replace them, and combine with each other.

SQLite free text search with stemming uses a separate FTS table (the porter tokeniser), set with `SetStemmingTable`, and also needs the custom query generator (`UseFreeTextSearchExtensions` calls `UseCustomQueryGenerator` on SQLite). `SqliteFreeTextSearchTranslator` translates `FreeTextSearch` into `MATCH(text, column, stemmingTable)`: the third argument is the stemming table name of the column's table, or `NULL` without stemming (it throws "Stemming table not specified" if stemming is asked for and the column's table has none). `SqliteCustomQueryGenerator.GetCommand` finds the first such `MATCH` on each table alias before any SQL is written (`StemmingTableFinder`), `VisitTable` writes the stemming table in place of the table, keeping the alias, for each alias whose first search uses stemming, and `VisitSqlFunction` writes the `MATCH` without its third argument. So each use of a table in a query (each side of a self join, a subquery, each part of a union) has its own `useStemming`, and only the first call on the same alias counts (documented limitation, see `ReadMe.md`). Rows are read from the stemming table, which must have the same column names, but it doesn't need to be in the model. The alias is read from the `MATCH`'s column when the SQL is generated, never copied into another argument, because EF Core can rename aliases after translation (e.g. a subquery pushdown); EF Core makes aliases unique across the whole query, so one dictionary covers subqueries and set operations. Everything comes from the SQL tree, so EF's SQL cache stays correct. `ExecuteDelete` / `ExecuteUpdate` with a stemming search in the `Where` change the stemming table, not the table being searched (as the `SqliteFreeTextSearchInterceptor` that this replaced in 7.0.0.0 did). Two other designs were tried and rejected (see the ChangeLog): matching the stemming table's rows back by ROWID in a LINQ subquery needed a property mapped to ROWID on both tables, and building the subquery in the translator from `SqlFragmentExpression`s worked only as a correlated `EXISTS`, because EF Core turns a one-value `IN` into `=`.

A translator can find the collation of the column it's translating, but **not through `IColumn.Collation` or `IProperty.GetCollation()`**. Both throw an `InvalidOperationException` in a query ("The requested configuration is not stored in the read-optimized model"), because EF leaves collations out of the runtime model (only migrations need them). `SqliteNoCaseTranslator` (`CaseInsensitivity/`) uses this to make SQLite's string functions honour NOCASE. A trial against EF 11.0.0 on SQLite found the following. The column is the translator's `instance` (or one of its `arguments`).
- A table column arrives as a `ColumnExpression` whose `Column` (`IColumnBase`) is set: for a plain column, through a reference or collection navigation (`SqliteNoCaseTranslatorTests_012` / `_013`, with the `NavigationParent` / `NavigationChild` test entities, added to the model only in those tests), on either side of a join, after `SelectMany`, after a projection, and when selected from a subquery or a set operation (`SqliteNoCaseTranslatorTests_009` / `_010`; this matches SQLite, which keeps a subquery column's collation and gives a compound SELECT's column the collation of the leftmost SELECT). `Column.PropertyMappings` leads back to the runtime `IProperty`.
- The collation is read from **`IDesignTimeModel`**, injected into the translator plugin: look up the same entity type and property in `designTimeModel.Model`, where `GetCollation()` works. EF builds the design-time model the first time it's used (once per model). This covers a collation set with `UseCollation` as well as `UseCaseInsensitiveCollation`, with no model convention needed. (A custom annotation set alongside the collation also works, as custom annotations are kept in the runtime model, but it was rejected because only collations set by the library would carry it.) Only properties of entity types are looked up, so a property of a complex type has no known collation.
- `EF.Functions.Collate(..., "NOCASE")` arrives as a `CollateExpression` with `Collation` on it directly.
- A concatenation (`||`), `COALESCE` (`??`) or `CASE` (a conditional) takes the collation of its operands: NOCASE when its operands with a known collation are all NOCASE (constants, parameters and columns without a collation don't count; different collations give no known collation). `SqliteNoCaseTranslator.GetCollation` / `GetCombinedCollation` do this recursively.
- Anything else has no known collation: a function EF Core translated (e.g. `Substring` on a column that isn't NOCASE), a number converted to a string, or a column from raw SQL, where `Column` is `null`. The translator should then return `null`, so EF's own translation is used. (The string methods the translator handles on a NOCASE column, `Replace`, `Substring`, `ToLower` / `ToUpper` and the `Trim` methods, wrap their result in `COLLATE NOCASE`, so a method called on the result is translated too.)
- EF's compiled query cache key includes the model, so a translation that depends on the model's collations is cached per model and stays correct.

`SqliteNoCaseTranslator.IsNoCase` / `GetCollation` do this:

```csharp
string? collation = expression switch
{
    CollateExpression collateExpression => collateExpression.Collation,
    ColumnExpression { Column: { } column } => this.GetCollation(column), // the first entity type property in column.PropertyMappings with a collation in the design-time model
    _ => null,
};
```

### Other notable pieces

- `Utilities/` — small extension classes, one per feature and named after what they do (as the other `*Extensions` classes are), all in the `Utilities` namespace: `GuidExtensions` (`CreateGuid`), `DatabaseExistsExtensions` (`DoesDatabaseExistAsync`), `GetDbContextExtensions` (`GetDbContext`), `DelimitedIdentifierExtensions` (`GetDelimitedIdentifier`) and `UniqueConstraintExtensions` (below). They replaced the single `UtilityExtensions` class in 7.0.0.0 (`CaseInsensitiveCollationExtensions` was split out at the same time, then moved to `CaseInsensitivity/`).
- `Utilities/UniqueConstraintExtensions.cs` — `IsUniqueConstraintException()`, an extension method on `Exception` that searches the exception and its inner exceptions and returns `true` for a unique index, unique constraint or primary key violation. It checks error codes only, never the message (which SQL Server translates), and needs no `DbContext`: SQL Server `SqlError.Number` 2601 or 2627 anywhere in `SqlException.Errors`; SQLite `SqliteExtendedErrorCode` `SQLITE_CONSTRAINT_UNIQUE` / `SQLITE_CONSTRAINT_PRIMARYKEY` (not `SqliteErrorCode`, which is 19 for every constraint violation, including NOT NULL). In 7.0.0.0 it replaced `UniqueConstraintInterceptor`, `UniqueConstraintException` and `UniqueConstraintDetails`, whose table / field name lookup was unreliable; see the ChangeLog before adding anything like it back.
- `Execute/ExecuteMethods.cs` — raw SQL execute helpers behind the public `DatabaseFacade` extensions in `ExecuteExtensions.cs` (`ExecuteScalarAsync`, `ExecuteQueryAsync`, `ExecuteNonQueryAsync`, `ExecuteInsertAsync`, `ExecutePagedQueryAsync`). The SQL here is written by the library's caller, not generated by EF Core, so it can contain comments, strings and quoted identifiers anywhere. Don't confuse `DatabaseFacade.ExecuteInsertAsync<T>(sql, ...)` (raw SQL, here) with `IQueryable<TSource>.ExecuteInsertAsync(setters)` (EF-generated SQL, in `ExecuteUpdate/`). `ExecutePagedQueryAsync` and `GetLastInsertId` (used by `ExecuteInsertAsync`) use `SqlParser/` to rewrite the SQL rather than regex.
- `SqlParser/` — a small tokenizer (not a full SQL parser) used to build the paged and count queries and the "get last insert id" query. `SqlDialect` is the abstract base, with `SqliteDialect` / `SqlServerDialect` overriding what differs: quotes, whether block comments nest (SQL Server) and whether an unclosed `/*` is allowed to run to the end (SQLite), trailing clauses (`LIMIT`, `OPTION`, `FOR XML`...) and how a query is paged. `Tokenize` skips whitespace and comments and tracks bracket depth. `Analyse` splits a SELECT into a `SqlQueryShape` (prefix / query / outer `ORDER BY` / tail), using positions in the original string so the caller's formatting and `{0}` placeholders are kept. Anything the library adds must be appended after the end of the last token, and on a new line, so it can never end up inside a caller's trailing comment. The tokenizer tests (`Tests/SqlParser/SqlDialectTests.cs`) need no database. Tests that run the generated SQL are in `Tests/Execute/ExecutePagedQueryTests.cs` and `ExecuteInsertTests.cs`.
- `CaseInsensitivity/` — case insensitivity, in the `CaseInsensitivity` namespace. `CaseInsensitiveCollationExtensions` (`UseCaseInsensitiveCollation`, both databases) sets a case insensitive collation in the model: `Latin1_General_100_CI_AS_SC_UTF8` on SQL Server (the database collation), `NOCASE` on every string property on SQLite. `SqliteNoCaseReplacementExtensions` (`UseSqliteNoCaseReplacement`, SQLite only) replaces SQLite's ASCII-only `NOCASE` collation with a Unicode one matching the SQL Server collation, via `SqliteNoCaseReplacementInterceptor`. The interceptor is a `DbCommandInterceptor` that registers everything in `CommandCreated`, once per `SqliteConnection` object (tracked in a `ConditionalWeakTable`), not in `ConnectionOpened`, which EF Core doesn't raise for a connection that was already open when it was given to EF Core (e.g. an in-memory database). Once is enough because Microsoft.Data.Sqlite keeps the registrations on the connection object and applies them again each time it's opened. The registrations themselves are in the public `UseSqliteNoCaseReplacement(this SqliteConnection)` overload, which the interceptor calls (callers use it on a `SqliteConnection` used without EF Core); the interceptor only records the connection after it succeeds, so a failed registration is retried on the next command. A connection that isn't a `SqliteConnection` (e.g. a profiling wrapper around one) throws an `InvalidOperationException` naming its type, rather than NOCASE silently staying ASCII only (`CaseInsensitivityTests_009`, with the `WrappedSqliteConnection` test helper). The registrations replace the built-in `lower` and `upper` with Unicode versions and add the `nocase_*` functions (`nocase_instr`, `nocase_like`, `nocase_replace`, `nocase_trim` / `nocase_ltrim` / `nocase_rtrim`, `nocase_startswith`, `nocase_endswith`), implemented in `SqliteUnicodeMethods` with the names in `SqliteUnicodeFunctionNames`. `SqliteNoCaseTranslator` (registered as a plugin, `SqliteNoCaseTranslatorPlugin`) translates `Contains`, `IndexOf`, `StartsWith`, `EndsWith`, `Replace`, `Trim` / `TrimStart` / `TrimEnd` and `EF.Functions.Like` into the `nocase_*` functions when the column is NOCASE (above); otherwise it returns `null` and EF Core's own translation is used. The string results (`Replace`, `Substring`, `ToLower` / `ToUpper` and the `Trim` methods, with or without characters) are wrapped in `COLLATE NOCASE`, as SQL Server gives a function's result its argument's collation, so comparing them or calling another method on them ignores case too; `Substring`, `ToLower` / `ToUpper` and `Trim()` without characters use EF Core's own SQL (`substr`, the `lower` / `upper` replacements, `trim`) with only the collation added. The built-in `instr`, `like` and so on are left alone, because a SQLite function can't see its arguments' collation. Concatenation, `??` and conditionals aren't method calls, so the translator never sees them: `SqliteNoCaseQueryExpressionInterceptor` (an `IQueryExpressionInterceptor`, also registered by `UseSqliteNoCaseReplacement()`) wraps each one (only the outermost of a chain) in a call to the `KeepCollation` marker method before EF Core translates the query, and the translator always translates the marker, returning the translated expression with `COLLATE NOCASE` if it's NOCASE (above), otherwise unchanged. The marker must always be translated, never return `null`. `KeepCollation` returns its value unchanged when EF Core evaluates it on the client (a concatenation with a method EF Core can't translate, in the final projection), unlike `Match` / `FreeTextSearch`, which throw: the interceptor adds it to the user's own query, which worked before. The `UseSqliteNoCaseReplacement(SqliteConnection)` overload only registers the collation and functions; it doesn't translate anything.

## Code style

Files consistently use `#region`/`#endregion` blocks to group members (e.g. `#region public methods`, `#region private constants`), and every public member has full XML doc comments (`GenerateDocumentationFile` is enabled and used to publish API docs via `DefaultDocumentation`). Match this structure in new/edited files.

**Test classes are an exception to the global region rule** (which would put the `[TestMethod]`s in `#region public methods`). Here a test class has `#region private constants` (its `const` members, if it has any), `#region private fields` (the `TestContext`), `#region public constructors`, `#region test lifecycle` if it has `[TestInitialize]`, `[ClassInitialize]`, `[GlobalTestCleanup]` etc. (e.g. `SqliteSqlServerEquivalenceTests`, `SqliteTestCleanup`), then one `#region <Feature> tests` per method or feature being tested (e.g. `#region WithTableHints tests`, `#region nocase_instr tests`), then `#region private methods` for helpers. Follow this, not `#region public methods`.

`ArgumentNullException.ThrowIfNull(...)` (or `ArgumentException.ThrowIfNullOrEmpty`) is the standard guard-clause style at the top of public methods.
