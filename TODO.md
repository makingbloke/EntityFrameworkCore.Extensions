#### Bugs

7. **On SQLite, the raw SQL `ExecuteInsertAsync` returns an unrelated id when nothing was inserted** (medium-high, reproduced).
   * **Why:** `SELECT LAST_INSERT_ROWID()` (`ExecuteMethods.cs:226`) returns the last insert on that connection, which pooling keeps between contexts.
   * **Example:** an `INSERT OR IGNORE` that hit a duplicate returned another table's id. SQL Server's `SCOPE_IDENTITY()` gives `default(T)` instead.
   * **Reopened (25 November 2026): the method should return the new row's Id, which could be a GUID, not the ROWID.** The `changes()` fix below was made and then undone, as it only fixes identity / rowid keys.
     * **The current approach can never return a GUID key, on either database.** On SQLite, `last_insert_rowid()` is the hidden rowid, which a table with a GUID primary key still has, but which is no use to the caller. On SQL Server, `SCOPE_IDENTITY()` only returns an `IDENTITY` column's value, so a GUID key gives `NULL` (`default(T)`).
     * **The library has to name the key column in the SQL to return it**, and raw SQL has no entity type, so the caller has to say which column it is, one way or another.
     * **Where the GUID comes from:**
       * generated in code (e.g. `CreateGuid()`, then passed as a parameter): the caller already has the Id before the insert, so `ExecuteNonQueryAsync` is enough;
       * generated by the database (e.g. a `NEWSEQUENTIALID()` default on SQL Server; rarer on SQLite, which has no GUID function): only `RETURNING` / `OUTPUT` can return it.
     * **Options (to decide):**
       * **i. Add a key column parameter**, e.g. `ExecuteInsertAsync<Guid>(sql, keyColumn: "Id", ...)`.
          * SQLite: add `RETURNING "Id"` at the end of the statement (the tokenizer already finds where the SQL ends).
          * SQL Server: `OUTPUT INSERTED.[Id]` has to go before `VALUES` / `SELECT` / `DEFAULT VALUES`, so the tokenizer has to find that point. Plain `OUTPUT` fails on a table with triggers (error 334), so the safe form is `OUTPUT INSERTED.[Id] INTO @ids` (a table variable, with a `sql_variant` column to cover most key types) followed by `SELECT ... FROM @ids`.
          * The most work, but the same call works on both databases for any key type. `RETURNING` / `OUTPUT` return no row when nothing is inserted, so the `changes()` fix isn't needed.
       * **ii. Keep it identity / rowid only, and document it.** For other keys: generate the Id in code and use `ExecuteNonQueryAsync`, or write `RETURNING` / `OUTPUT` yourself and use `ExecuteScalarAsync`. For an entity in the model, `ExecuteInsertGetRowAsync` already returns the whole row, whatever its key. With this option, still make the `changes()` fix.
       * **iii. Remove `ExecuteInsertAsync`**, with the same pointers as option ii, if returning only identity / rowid isn't worth keeping.
   * **The `changes()` fix (made, then undone; only needed for option ii):** on SQLite, add `SELECT CASE WHEN changes() > 0 THEN last_insert_rowid() END` instead of `SELECT LAST_INSERT_ROWID()`. It runs in the same command as the caller's INSERT, so `changes()` is that INSERT's count, and nothing inserted gives `NULL`, so `default(T)`, as SQL Server's `SCOPE_IDENTITY()` already does.
     * **Document** in the `ExecuteInsertAsync` remarks:
       * it returns the identity value (SQL Server) or rowid (SQLite) of the inserted row, or `default(T)` if nothing was inserted;
       * for an entity in the model, `ExecuteInsertGetRowAsync` returns the whole row, whatever its key type;
       * for raw SQL with another key type or more columns, write `INSERT ... RETURNING ...` (SQLite) / `OUTPUT INSERTED...` (SQL Server) and use `ExecuteScalarAsync` or `ExecuteQueryAsync`.
     * **Tests:**
       * SQLite: `INSERT OR IGNORE` hitting a duplicate, and `ON CONFLICT DO NOTHING`, each after an insert into another table, return 0;
       * both databases: an `INSERT ... SELECT ... WHERE NOT EXISTS` that inserts nothing returns 0.
   * **Options considered earlier and rejected** (before the GUID point was raised):
     * **Remove `ExecuteInsertAsync`** (or mark it `[Obsolete]`) and point callers to `ExecuteScalarAsync` with `RETURNING` / `OUTPUT`. It would only remove this item, and callers would have to write the id part differently for each database (`RETURNING` goes at the end, `OUTPUT` in the middle), and on SQL Server `OUTPUT` without `INTO` fails on a table with triggers.
     * **Rewrite the caller's INSERT to add `RETURNING` / `OUTPUT`**, throwing if the clause is turned off as the `...GetRowsAsync` methods do. Raw SQL has no entity type, so `UseSqlOutputClause(false)` / `UseSqlReturningClause(false)` can't be checked without guessing the table from the SQL. Placing `OUTPUT` needs the tokenizer to find the point before `VALUES` / `SELECT` in any INSERT. The key column isn't known either, so it could still only return the identity / rowid, the same as now.
